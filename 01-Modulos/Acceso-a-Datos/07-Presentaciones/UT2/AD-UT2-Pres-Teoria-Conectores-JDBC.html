1. ¿Qué es JDBC y cuál es su Arquitectura?

Capa de abstracción estándar entre el código Java y los motores RDBMS relacionales

Arquitectura en Capas JDBC

Estándar Java SE

JDBC (Java Database Connectivity) desacopla la aplicación de las particularidades del motor SQL:

  • Java Application: Invoca interfaces estándar del paquete java.sql.
  • JDBC Driver Manager: Gestiona y enruta llamadas al conector adecuado.
  • JDBC Driver (Vendor): Implementa el protocolo binario del motor (Oracle, PostgreSQL, etc.).
  • Database Server: Ejecuta consultas y gestiona el almacenamiento transaccional.
💡 Analogía Cotidiana: El Adaptador de Corriente Universal

Imagina viajar por todo el mundo con tus dispositivos electrónicos. Cada país tiene un enchufe de pared diferente (Oracle, PostgreSQL, MySQL), pero tu cargador tiene siempre la misma clavija (tu código Java).

El Driver JDBC es el adaptador físico específico para cada país: la clavija de tu ordenador nunca cambia, pero el conector traduce al voltaje y geometría del enchufe local.

📌 El Conector Oracle Type 4 (Pure Java Thin Driver) En nuestro módulo utilizamos el driver oficial de Oracle ojdbc11. Es un conector de tipo 4: código 100% Java puro que se comunica directamente por TCP/IP con el puerto 1521 de Oracle sin requerir instalar clientes nativos C/C++ en el sistema operativo.

3. Statement vs PreparedStatement

Por qué la concatenación de texto en sentencias SQL es una práctica prohibida

❌ Statement (Peligroso)

Vulnerable a Inyección SQL 
// Peligro: inyección SQL inmediata
String sql = "SELECT * FROM usuarios WHERE email = '" 
             + txtEmail + "' AND pass = '" + txtPass + "'";
Statement st = conn.createStatement();
ResultSet rs = st.executeQuery(sql);

Si el usuario ingresa admin' OR '1'='1, la consulta altera su semántica y devuelve todos los registros saltándose la autenticación.

✅ PreparedStatement (Seguro y Rápido)

Compilación Previa 
// Seguro: parámetros posicionales '?'
String sql = "SELECT * FROM usuarios WHERE email = ? AND pass = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, txtEmail);
    ps.setString(2, txtPass);
    try (ResultSet rs = ps.executeQuery()) { ... }
}

El motor compila y optimiza el árbol de ejecución una sola vez. Los valores entran como parámetros tipados sin alterar el código SQL.

🚀 Ventaja Doble: Seguridad Absoluta + Caché de Ejecución en Oracle Oracle almacena los planes de ejecución en la Shared Pool (SGA). Usar PreparedStatement permite a Oracle reutilizar el plan existente para miles de llamadas con parámetros distintos (Soft Parse), disparando el rendimiento hasta un 400%.

6. Invocación de Procedimientos PL/SQL

Uso de CallableStatement con parámetros de entrada (IN) y salida (OUT)

Procedimiento Almacenado en Oracle

PL/SQL DDL 
CREATE OR REPLACE PROCEDURE sp_calcular_descuento (
    p_id_cliente IN NUMBER,
    p_total_compras OUT NUMBER,
    p_porcentaje_desc OUT NUMBER
) AS
BEGIN
    SELECT NVL(SUM(importe), 0) INTO p_total_compras
    FROM pedidos WHERE id_cliente = p_id_cliente;
    
    IF p_total_compras > 1000 THEN p_porcentaje_desc := 15;
    ELSE p_porcentaje_desc := 5;
    END IF;
END;

Invocación en Java

CallableStatement 
String sql = "{ call sp_calcular_descuento(?, ?, ?) }";
try (CallableStatement cs = conn.prepareCall(sql)) {
    cs.setLong(1, 105L); // Parámetro IN
    
    // Registrar parámetros OUT indicando el tipo SQL
    cs.registerOutParameter(2, Types.NUMERIC);
    cs.registerOutParameter(3, Types.NUMERIC);
    
    cs.execute(); // Ejecutar
    
    // Leer resultados
    double total = cs.getDouble(2);
    int descuento = cs.getInt(3);
}

7. Retorno de Conjuntos con SYS_REFCURSOR

Cómo devolver colecciones de datos completas desde funciones o paquetes Oracle

Función PL/SQL con SYS_REFCURSOR

Oracle 23c 
CREATE OR REPLACE FUNCTION fn_listar_empleados_dep(
    p_dep_id IN NUMBER
) RETURN SYS_REFCURSOR AS
    v_cursor SYS_REFCURSOR;
BEGIN
    OPEN v_cursor FOR
        SELECT id, nombre, salario 
        FROM empleados 
        WHERE id_departamento = p_dep_id;
    RETURN v_cursor;
END;

Consumo en JDBC con Types.REF_CURSOR

Java 21 
String sql = "{ ? = call fn_listar_empleados_dep(?) }";
try (CallableStatement cs = conn.prepareCall(sql)) {
    // Parámetro 1: Retorno de la función (Cursor)
    cs.registerOutParameter(1, Types.REF_CURSOR);
    cs.setInt(2, 10); // Departamento 10
    
    cs.execute();
    
    // Convertir el cursor devuelto a un ResultSet
    try (ResultSet rs = (ResultSet) cs.getObject(1)) {
        while (rs.next()) {
            System.out.println(rs.getString("nombre"));
        }
    }
}
⚡ Estándar JDBC 4.2 vs Cast Nativo En Java 8+ / JDBC 4.2+, Types.REF_CURSOR está estandarizado en el paquete java.sql.Types. Antes requería OracleTypes.CURSOR de la librería privativa. Ahora el código es portable y limpio.

8. Gestión Transaccional ACID en JDBC

Control manual de transacciones con setAutoCommit(false), commit() y rollback()

Las 4 Propiedades ACID

Bases de Datos Robustas
  • Atomicidad (All-or-Nothing): O se ejecutan todas las operaciones con éxito, o ninguna surte efecto.
  • Consistencia: La base de datos pasa de un estado válido a otro cumpliendo restricciones.
  • Aislamiento: Las operaciones simultáneas no interfieren entre sí.
  • Durabilidad: Una vez confirmado el commit, los cambios sobreviven a caídas eléctricas.

Patrón Transaccional Canónico

Try-Catch-Finally 
try (Connection conn = dataSource.getConnection()) {
    conn.setAutoCommit(false); // 1. Desactivar auto-confirmación
    try {
        debitarCuenta(conn, origenId, importe);
        acreditarCuenta(conn, destinoId, importe);
        
        conn.commit(); // 2. Confirmación atómica
    } catch (Exception e) {
        conn.rollback(); // 3. Deshacer en caso de error
        throw e;
    } finally {
        conn.setAutoCommit(true); // 4. Restaurar
    }
}
⚠️ El Peligro del Modo Auto-Commit por Defecto Por defecto, cualquier conexión JDBC tiene autoCommit = true. Esto significa que cada executeUpdate() confirma inmediatamente el cambio en disco. Si en una transferencia bancaria falla el ingreso tras haber retirado el saldo, ¡el dinero desaparecerá en el limbo si no gestionas la transacción manualmente!

9. Puntos de Retorno Parcial: Savepoints

Deshacer operaciones intermedias sin perder el trabajo previo de la transacción

¿Qué es un Savepoint?

java.sql.Savepoint

Un Savepoint actúa como un punto de restauración temporal dentro de una transacción activa:

  • conn.setSavepoint("nombre"): Marca el punto actual.
  • conn.rollback(sp): Deshace únicamente las operaciones posteriores al punto.
  • conn.releaseSavepoint(sp): Libera los recursos del punto intermedio.

Ejemplo: Proceso por Lotes con Fallo Parcial

Resiliencia 
conn.setAutoCommit(false);
Savepoint sp = conn.setSavepoint("PuntoClienteA");
try {
    procesarCobroCliente(conn, clienteA);
} catch (PaymentException pe) {
    // Solo deshacemos el cliente A, manteniendo el resto
    conn.rollback(sp);
    registrarFallo(clienteA);
}
// Continuamos con el resto de clientes del lote...
conn.commit();
💡 Analogía Cotidiana: Puntos de Guardado en Videojuegos Imagina jugar un nivel largo de un videojuego. Antes de enfrentarte a una trampa peligrosa, tocas un CheckPoint (Savepoint). Si mueres en la trampa, reapareces en ese punto sin tener que empezar el juego entero desde el principio (rollback total).

11. El Problema del DriverManager a Demanda

Por qué abrir y cerrar conexiones en cada petición de usuario colapsa el servidor

El Coste Oculto de una Conexión

~100-300 ms por Handshake

Cada vez que ejecutas DriverManager.getConnection(), ocurren los siguientes pasos en la red:

  • Apertura de Socket TCP/IP: Negociación de red (SYN, SYN-ACK, ACK).
  • Autenticación y Criptografía: Handshake SSL/TLS y validación de contraseñas.
  • Proceso Dedicado en Servidor: En Oracle, se crea un proceso servidor en Linux/Unix que consume memoria RAM fija (PGA).
  • Destrucción de Recursos: El cierre (close) exige liberar búferes y cerrar sockets.
💥 El Escenario de Colapso en Producción Si tu aplicación web recibe 200 peticiones concurrentes por segundo e intentas abrir 200 conexiones con DriverManager:
  • El tiempo de respuesta se degrada de 10ms a varios segundos.
  • La CPU del servidor de base de datos se satura gestionando handshakes en vez de procesar consultas SQL.
  • Oracle alcanza el límite MAX_PROCESSES y lanza el temido error ORA-00020: maximum number of processes exceeded.

En su lugar, tomas un taxi de la parada que ya está arrancado y disponible, lo usas durante el trayecto y lo dejas para que otro cliente lo use inmediatamente.

14. Implementación Canónica de un DAO

Tratamiento de excepciones personalizadas y mapeo limpio de ResultSet a Entidad

Método findById con Optional

Java 21 
@Override
public Optional<EmpleadoDTO> findById(Long id) {
    String sql = "SELECT id, nombre, email, salario FROM emp WHERE id = ?";
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        ps.setLong(1, id);
        try (ResultSet rs = ps.executeQuery()) {
            if (rs.next()) {
                return Optional.of(mapResultSet(rs));
            }
            return Optional.empty();
        }
    } catch (SQLException e) {
        throw new PersistenceException("Error al consultar empleado " + id, e);
    }
}

Método Helper de Mapeo

DRY (Don't Repeat Yourself) 
private EmpleadoDTO mapResultSet(ResultSet rs) throws SQLException {
    return new EmpleadoDTO(
        rs.getLong("id"),
        rs.getString("nombre"),
        rs.getString("email"),
        rs.getBigDecimal("salario")
    );
}

Centralizar el mapeo de columnas en un método privado garantiza que un cambio en la tabla solo requiera actualizar una única línea de código en todo el DAO.

🛡️ Enmascaramiento de Excepciones: PersistenceException Nunca propagues SQLException hacia las capas superiores (servicios o controladores web). Es una excepción chequeada muy acoplada a JDBC. El DAO debe capturarla y relanzar una excepción unchecked de dominio como PersistenceException, protegiendo la arquitectura.

16. Errores Típicos en Exámenes y Prácticas

Los 4 descuidos más comunes al programar con JDBC y cómo evitarlos

1. Olvido del rs.next()

Exhausted ResultSet

El cursor de un ResultSet apunta inicialmente antes de la primera fila. Si intentas llamar directamente a rs.getString("col") sin hacer previamente un if (rs.next()) o while (rs.next()), la aplicación lanzará un error de cursor no posicionado.

2. Fuga de Conexiones (Connection Leak)

Pool Agotado

No usar try-with-resources para cerrar conexiones o sentencias. Al cabo de 10 consultas, la piscina de conexiones se queda sin recursos disponibles (pool empty) y la aplicación se congela indefinidamente esperando que se libere una conexión.

3. Olvidar conn.setAutoCommit(true)

Conexión Sucia

Si devuelves al pool una conexión con autoCommit = false sin haber hecho rollback o sin restaurar el flag a true en el bloque finally, la siguiente consulta de otro hilo heredará ese estado transaccional sucio.

4. Fechas obsoletas de java.util.Date

API Anticuada

Usar java.util.Date en lugar de la moderna API java.time (LocalDate, LocalDateTime). Utiliza siempre ps.setObject(i, localDate) y rs.getObject(col, LocalDate.class).

17. Resumen de Clases e Interfaces Clave

Matriz de referencia rápida para el desarrollo con JDBC en Java 21

Componente Tipo Propósito Principal Métodos Críticos
Connection Interfaz Sesión activa con el motor RDBMS y delimitador transaccional. prepareStatement(), commit(), rollback(), close()
PreparedStatement Interfaz Sentencia SQL precompilada con parámetros tipados ('?'). setXxx(), executeQuery(), executeUpdate()
CallableStatement Interfaz Ejecución de procedimientos y funciones almacenadas (PL/SQL). registerOutParameter(), execute(), getXxx()
ResultSet Interfaz Cursor sobre la tabla de resultados de una consulta SELECT. next(), getXxx(), wasNull(), getMetaData()
HikariDataSource Clase Piscina de conexiones precalentadas de alta velocidad. getConnection(), close()
DatabaseMetaData Interfaz Catálogo global del motor de base de datos y soporte técnico. getTables(), getColumns(), getPrimaryKeys()
💡 Todas implementan AutoCloseable Todas las interfaces de JDBC heredan de java.lang.AutoCloseable. La regla de oro es declarar siempre las conexiones, statements y resultsets dentro de los paréntesis del bloque try (...).
